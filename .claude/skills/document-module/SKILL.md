# 레거시 모듈 문서화

`$ARGUMENTS` 의 첫 값은 분석할 모듈 경로, 둘째 값은 범위 제한(예: "검색 화면만")이다. 경로가 없으면 묻는다.

- 분석 대상 폴더의 파일은 읽기만 한다. 수정 · 이동 · 삭제 · 포맷팅을 하지 않는다.
- 소스를 읽어서 정리한다. 화면이나 DB 를 실행하지 않았으면 문서 머리말에 그렇게 적는다.
- 근거는 저장소 루트 기준 `파일:줄번호` 로 적는다. 근거 줄을 댈 수 없으면 "확인 필요"로 적는다.
- 규칙의 "근거" 줄에는 경로를 줄이지 않는다. 표 · 비고에서 경로를 줄여 쓰려면(`…/assign/`, 파일 이름만) 문서 머리말에 그 줄임이 가리키는 폴더를 적는다.
- 동작 전체가 기대는 전제(고정된 현재 시각, 실행 옵션, 환경 변수)를 찾으면 세 문서의 머리말에 근거 줄과 함께 적는다.

## 산출물

`docs/<모듈명>/ARCHITECTURE.md`, `ERD.md`, `BUSINESS-RULES.md` 세 개다.
`<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다.

| 모듈 경로 | 모듈명 |
|---|---|
| `legacy/item-bank-php` | `item-bank` |
| `legacy/assignment-thymeleaf` | `assignment` |
| `legacy/grade-mssql` | `grade` |

## 절차

단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다.

1. **계획 제시** — 읽을 파일 목록, 단계, 산출물 경로를 먼저 보여 준다. 파일은 아직 만들지 않는다.
2. **진입점** — URL(또는 호출부)마다 처음 실행되는 파일과 부르는 함수를 표로 정리한다. → `ARCHITECTURE.md`
3. **의존 관계** — 파일 포함 · 함수 호출 방향을 표와 mermaid 흐름도로 정리한다. → `ARCHITECTURE.md`
4. **데이터 흐름** — 테이블 · 뷰, 관계(선언 / 추정 구분), 읽기 · 쓰기 위치를 정리한다. → `ERD.md`
   - 이 모듈이 쓰는 테이블 이름을 `legacy/`, `modern/`, `db/` 에서 검색해 같은 테이블을 쓰는 다른 모듈을 읽기 / 쓰기로 나눠 적는다. JPA 는 `@Table` 엔티티의 값을 바꾸는 메서드와 그 호출부까지 읽는다.
   - 스키마 제약(NOT NULL · FK · UNIQUE)과 시드를 코드와 대조한다. 제약 때문에 닿지 않는 분기, 코드의 검사와 어긋나는 시드 행을 "눈에 띄는 점"에 적는다.
5. **비즈니스 규칙 후보** — 조건문 · SQL 에서 규칙을 뽑아 아래 형식으로 적는다. → `BUSINESS-RULES.md`
   - 같은 조건이 화면(템플릿) · 컨트롤러 · 서비스 · SQL 에 따로 구현돼 있으면 서로 대조하고, 다른 점을 비고에 적는다.
6. **표본 점검 추천** — 사람이 직접 코드와 대조할 규칙 3개를 추천한다. 가장 그럴듯해 보이는 규칙을 반드시 1개 포함하고, 나머지는 근거가 여러 파일에 걸친 규칙과 주석 · 코드가 다른 규칙에서 고른다. 각각 고른 이유와 확인할 `파일:줄번호` 를 적는다.
7. **자체 검수** — 세 문서를 저장한 뒤 아래를 확인하고, 고친 곳을 답변에 표로 적는다.
   - 문서의 모든 `파일:줄번호` 가 실제 파일의 줄 범위 안에 있다. 줄여 쓴 경로도 빼지 않는다.
   - 규칙마다 "근거 코드"의 각 줄이 "근거"에 적은 줄 범위 안에 글자 그대로 있다.
   - 규칙 ID 가 빠짐없이 이어지고, 다른 규칙을 가리키는 ID 가 존재한다.
   - 파일 수 · 줄 수 · 건수는 세어서 적은 값이다.

각 문서 끝에는 "미확인 목록"(항목 / 미확인 사유)을 둔다.

## 규칙 형식

```markdown
#### BR-01
- 규칙: <조건>이면 <결과>한다. (한 문장)
- 근거: legacy/<모듈>/<파일>:<줄번호>
- 근거 코드:
  ```php
  <근거 줄을 그대로 인용>
  ```
- 확신도: 확실 | 추정
- 비고: <매직 넘버, 주석과 코드 불일치, 같은 규칙의 다른 구현 위치>
```

- 코드 블록의 언어는 근거 파일에 맞춘다(`php`, `java`, `sql`, `html`).
- 구간 · 분류처럼 분기가 여럿인 규칙은 분기마다 조건 / 결과 / 줄번호를 한 행씩 표로 적는다.
- 확신도 "확실"은 조건문 · SQL 로 확인한 것, "추정"은 이름이나 주석으로 짐작한 것이다.
- 주석 · 안내 문구에만 있는 내용은 규칙으로 올리지 않고 "규칙으로 올리지 않은 것" 표에 모은다.
- 매직 넘버는 값 / 위치 / 추정 의미 표로 따로 정리한다.
- 규칙을 나중에 추가할 때는 기존 ID 를 바꾸지 않고 마지막 번호 다음을 쓴다.

## 하지 말 것

`docs/item-bank/BUSINESS-RULES.md` 의 "검증 이력"에서 실제로 틀렸던 유형이다.

- 입력값 정규화(`trim`, `strtolower`)를 한 변수에만 적지 않는다. 같은 처리를 받는 변수를 모두 적는다. (`sort` 만 적고 `dir` 을 빠뜨림)
- 여러 분기에 흩어진 공통 동작을 비고에만 나눠 적지 않는다. 독립 규칙으로 올린다. ("경고는 검색을 막지 않는다"가 빠짐)
- 입력 분기를 뭉뚱그리지 않는다. 빈 문자열 · `0` · 음수 · 숫자가 아닌 값을 각각 코드에 넣어 따라가 본다. (`0` 과 `-1` 을 "0 이하"로 묶음, 빈 `page` 누락)
- 경고 · 오류가 나오는 조건을 생략하지 않는다. 안쪽 `if` 까지 읽는다. (빈 `dir` 은 경고가 없는데 "경고 후 비운다"로 적음)
- 모듈 폴더 밖이라는 이유로 뷰 · 스키마 정의를 건너뛰지 않는다. 쿼리가 참조하는 정의는 읽기만 하고 근거로 적는다. (뷰의 `status = 'A'` 미확인)
- 다른 규칙을 가리키는 ID 를 기억으로 적지 않는다. 저장 전에 참조 번호를 다시 대조한다. (BR-26 을 BR-24 로 적음)
- 실행하지 않은 동작을 "확실"로 적지 않는다. 콜레이션 · 정렬 순서 · 제약 위반처럼 DB 가 결정하는 것은 미확인 목록에 넣는다.
- 존재하지 않는 함수 · 파일을 적지 않고, 호출 방향을 뒤집어 적지 않고, 코드에 없는 규칙을 만들지 않는다.

`docs/assignment/` 를 만들 때 검수에서 고친 유형이다.

- 검색 · 읽기로 바로 확인되는 것을 미확인 목록에 넣지 않는다. 미확인은 실행해야 알 수 있거나 저장소 밖에 있는 것만이다. (다른 모듈의 `distribution` 쓰기, 시드 행의 줄번호를 미확인으로 적음)
- 파일 수 · 줄 수를 어림으로 적지 않는다. (Java 소스 14개를 12개로 적음)
- 경계값을 한쪽만 적지 않는다. 기준 시각의 앞과 뒤, 같음 · 초과 · 미만을 각각 따라간다. (마감 "정각"을 마감 후만 적음)
- 주장과 다른 것을 가리키는 줄을 근거로 달지 않는다. (쓰기 동작이 둘이라는 문장에 메뉴 줄을 근거로 닮)
- 다른 문서를 가리키는 것으로 근거를 대신하지 않는다. `파일:줄번호` 를 적는다. ("ERD.md 참고"로 적음)
