# 머지 전 검증

검증 대상: $ARGUMENTS

- 인자가 비어 있으면 `git diff upstream/main...HEAD` 를 검증 대상으로 삼는다.
- 이 Skill 은 판정만 한다. 만든 쪽과 검증하는 쪽을 분리하는 절차이므로, 코드를 고치기 시작하면 검증자가 아니게 된다.
- 절차의 배경과 역할 분담은 저장소 루트의 `templates/verification-loop.md` 를, 판정 항목과 심각도 정의는 저장소 루트의 `templates/approval-checklist.md` 를 따른다. 체크리스트 항목은 이 문서에 옮기지 않고 그 파일을 직접 읽는다.

## 1. 절차

- reviewer 또는 tester Sub-agent 가 없는 환경에서는 (3) · (4) 를 기존 방식대로 메인 세션이 직접 수행한다.

### (1) 요청 범위 확인

- 이 변경이 무엇을 요청받은 것인지 한 문장으로 확인한다. 인자나 대화에서 찾을 수 있으면 그 문장을 그대로 쓴다.
- 요청 문장이 주어지지 않았으면 **판정하지 말고** 먼저 사람에게 묻는다. 요청 범위를 모르는 채로 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.

### (2) 변경 파일 목록과 diff 읽기

- `git diff --stat <범위>` 로 변경 파일 목록을 먼저 본다. patch 파일이면 `git apply --stat <파일>` 로 목록을 뽑는다.
- 파일마다 diff 를 읽는다. 판단에 문맥이 필요하면 해당 파일의 앞뒤 줄을 Read 로 읽는다.
- 변경 파일을 `modern/api` · `modern/web` · `characterization` · 그 밖(`legacy/`, `db/*/init/`, 설정 · 의존성 파일 등)으로 나눠 둔다. (4) 에서 실행할 테스트를 이 분류로 고른다.

### (3) 체크리스트 대조

- 직접 대조하지 않고 reviewer Sub-agent 에 위임한다.
- (2) 의 비교 범위(diff 범위 · 브랜치 · patch 파일)와 (1) 의 요청 문장을 바꾸지 않고 그대로 넘긴다.
- reviewer 에게 아래를 요청하고, 항목별 결과와 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향)을 돌려받는다.
  - 저장소 루트의 `templates/approval-checklist.md` 를 읽고, 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다.
  - 컨벤션 기준은 저장소 루트의 `CLAUDE.md` 를 기준으로 본다.
  - 이슈마다 심각도를 체크리스트의 심각도 정의(치명 / 경고 / 제안)에 따라 매긴다.

### (4) 테스트 실행

- 직접 실행하지 않고 tester Sub-agent 에 위임한다. 비교 범위와 (2) 의 변경 파일 분류, 아래 표와 조건을 그대로 넘긴다.
- 새 로직에 테스트가 없으면 tester 가 테스트 파일을 추가한 뒤 실행하게 한다.
- tester 에게서 추가한 테스트 파일 목록, 실행 명령, 통과 · 실패 수, 실패한 테스트 이름, 실행하지 못한 명령과 그 이유를 돌려받는다.

변경된 폴더의 테스트만 실행한다. 바뀌지 않은 모듈의 테스트는 돌리지 않는다.

| 바뀐 곳 | 명령 (저장소 루트 기준) |
|---|---|
| `modern/api` | `cd modern/api && ./gradlew test` |
| `modern/web` | `cd modern/web && npm test` |
| 이관 코드 (레거시 동작을 새 API 로 옮긴 변경) | `cd characterization && npm test` (레거시 대상) 와 `cd characterization && TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) 를 둘 다 실행 |

- 사용량을 아끼기 위해 전체 로그를 대화에 싣지 않는다. 출력은 scratchpad 의 파일로 보내고, 그 파일에서 통과 · 실패 수와 실패한 테스트 이름만 뽑아 남긴다.
- characterization 은 대상 서버가 떠 있어야 돈다(레거시 기본 주소는 `characterization/lib/target.mjs`, 새 API 는 8080). 서버가 꺼져 있거나 의존성이 설치되지 않아 실행할 수 없으면 서버를 직접 띄우지 말고 그 사실을 적은 뒤 사람에게 기동을 요청한다. 해당 기준은 "확인 필요"로 둔다.

### (5) 승인 기준 판정

- reviewer 와 tester 의 보고를 모두 받은 뒤 메인 세션이 네 기준을 모두 최종 판정한다. Sub-agent 의 판정을 그대로 옮기지 않는다.
- reviewer 와 tester 의 보고가 엇갈리면 엇갈린 지점을 그대로 적고, 판정하지 말고 사람에게 묻는다.
- 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 충족 · 미충족으로 판정한다.
- 네 기준이 모두 충족이어야 승인이다. 하나라도 미충족이면 반려다.
- 이슈가 0건으로 나오면 경고 · 제안 수준까지 diff 를 한 번 더 본 뒤에 판정한다.

## 2. 출력 형식

아래 순서를 바꾸지 않는다.

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 순서로 네 항목을 모두 채운다.
- 이슈가 없으면 표 대신 "이슈 없음"이라고 적는다.
- 판정하지 못한 것과 근거 줄을 대지 못한 지적은 이슈 목록 아래 "확인 필요" 목록에 한 줄씩 적는다.

## 3. 하지 말 것

- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 보고만 한다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다. 실행하지 못했으면 "실행하지 않음"과 그 이유를 적는다.
- 테스트 전체 로그를 대화에 싣지 않는다.
